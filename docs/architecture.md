# PickLeague — Architecture (v1)

PickLeague helps a player (a support main first, but every role is covered) pick the right champion in League of Legends champion select and then build it: items + buy order, runes, summoner spells, skill order — all adapted to the 9 other champions, **always showing the reasons** behind every recommendation.

Data comes from high-elo ranked solo/duo games (Challenger + Grandmaster + Master players of KR, EUW1, NA1, VN2, tracked from the top of the ladder down). The latest patch is collected, and on each platform the previous one too until that platform's first match of the latest patch is stored; the previous patch then stays in the database until the next one replaces it.

| `apps/worker` | `@pick-league/worker` | Riot crawler: rate limiter, priority scheduler, ingestion, patch detection, cleanup |
| `apps/api` | `@pick-league/api` | HTTP API, read-only on match data: static data, pick + build recommendations (the "engine"), caching, per-IP rate limit, gateway token, timer-driven stats refresh |
| `apps/desktop` | `@pick-league/desktop` | Electron helper: reads champion select from the League client, shows picks + builds with reasons, auto-applies runes + summoner spells on lock-in, keeps the build on screen until the game ends |

The server side (Postgres, worker, API, Caddy) runs with `docker compose up -d` on a Linux VPS. The web app runs on Vercel and is the only caller of the API; the desktop app runs on the player's computer (it must reach the local League client) and calls the API through the web app's gateway, so the VPS address is never handed out.

## Tooling

- Bun ≥ 1.3 workspaces (`packages/*`, `apps/*`), TypeScript strict, Biome, `bun test`.
- Root scripts: `check` (biome), `typecheck` (tsc -b or per package), `test`.
- Postgres client: `postgres` (porsager). No ORM; migrations are plain `.sql` files in `packages/db/migrations/NNNN_name.sql`, applied in order by a small runner that records them in `schema_migrations`. Migrations run automatically when the worker and the API start (idempotent, guarded by an advisory lock).

## Riot API facts the worker relies on

- **Hosts.** Platform host `https://{platform}.api.riotgames.com` (`kr`, `euw1`, `na1`, `vn2`) for league-v4, champion-mastery-v4. Regional host `https://{cluster}.api.riotgames.com` for match-v5 and account-v1. Match clusters: KR→`asia`, EUW1→`europe`, NA1→`americas`, VN2→`sea`. account-v1 is not served on `sea`: use `asia` for VN2 accounts.
- **Rate limits are enforced per host (routing value).** App limit (this key): 20 req / 1 s and 100 req / 2 min per host. Method limits also exist per endpoint. Read the real limits from `X-App-Rate-Limit`, `X-Method-Rate-Limit` (+ `-Count`) response headers rather than hardcoding; on `429` honour `Retry-After`. One limiter per host, so the 4 platforms + 4 clusters progress independently.
- **Never use a second API key** to go faster (Riot policy).
- Endpoints:
  - `GET /lol/league/v4/challengerleagues/by-queue/RANKED_SOLO_5x5`, `.../grandmasterleagues/...`, `.../masterleagues/...` (every Master player: the worker keeps the top ones by LP) → entries with `puuid`, `leaguePoints`, `wins`, `losses`.
  - `GET /lol/league/v4/entries/by-puuid/{puuid}` → solo rank of any player (low priority).
  - `GET /lol/champion-mastery/v4/champion-masteries/by-puuid/{puuid}`.
  - `GET /riot/account/v1/accounts/by-puuid/{puuid}` → `gameName`, `tagLine`.
  - `GET /lol/match/v5/matches/by-puuid/{puuid}/ids?queue=420&type=ranked&startTime={epochSeconds}&count=100`.
  - `GET /lol/match/v5/matches/{matchId}` and `.../{matchId}/timeline`.
- **Patch.** Data Dragon `https://ddragon.leagueoflegends.com/api/versions.json`, first entry is latest (`15.22.1`). A match's `info.gameVersion` (`15.22.715.1234`) belongs to patch `major.minor`. Data Dragon may lag the live patch by hours: a match from a patch newer than Data Dragon stays `PENDING` and is retried later. It may also be about a day *ahead* of the live servers (a patch published before any server plays it): each platform then keeps collecting the previous patch until it has stored a match of the new one, and the API keeps serving the previous patch until the stats have matches of the new one.

## Worker

Long-running Bun process. Each platform runs its own loop; work is pulled from priority levels, highest first, as long as rate-limit budget allows:

1. **Ladder refresh** (once per hour per platform): Challenger + Grandmaster lists, plus the top N of the Master list by LP. N starts at 0 (fresh database) and grows by 500 each time the platform has caught up: no listing waiting and at most 50 PENDING matches (checked every minute; the refresh with the larger N runs right away). After a restart N is the number of Master players in `ladder_entries`. More Master players is the lever for more data, not a longer history. Upsert `players` + `ladder_entries`. Players whose `wins + losses` changed (or are new) are marked "played" (`players.listing_requested_at`, so a restart loses nothing; cleared when a listing that started after it finishes).
2. **Match id listing** for "played" players, best ladder position first (Challenger by LP, then Grandmaster, then Master), using `startTime = players.matches_synced_until` (first time: start of the current patch as far as we know, else 14 days ago), paginating until exhausted. New ids of the player's own platform go to `match_fetch_queue` with the player's ladder position as `fetch_rank` (a match listed by several players keeps the best one). A player who plays again during their listing is listed again; a failed listing is retried after a cooldown (5 min, doubling up to 6 h).
3. **Match + timeline fetch** from the queue, lowest `fetch_rank` first (retried and deferred matches go to the back). Parse, keep only schema fields, insert everything in one transaction (matches, teams, bans, participants + per-minute arrays, item/skill/kill/objective events, `players` rows for all 10 players with their Riot ID from the payload). Matches of a patch that is no longer collected (older than the previous one, or the previous one once the latest is live on the platform) → `SKIPPED_OLD_PATCH` before their timeline is fetched; the first one seen bounds every listing (paginating stops there) and every pending id below it is skipped in one statement. After a patch change (and at startup) the backlog is probed by game id (highest pending first, then medians between the old and current bounds), so a stale backlog costs O(log n) requests instead of one each. Errors: transient ones (Riot 429/5xx after the client's retries, network, database connection) defer the match without counting an attempt (`FAILED` after 10) and back the loop off (5 s doubling to 5 min); deterministic ones (404, other 4xx, parse) fail it on the second attempt; anything else on the fifth. Non-ladder players are enqueued into `player_enrichment_queue` (respecting the 7-day rule).
4. **Daily refresh of tracked ladder players**: account-v1 (Riot ID) + mastery, if older than 24 h.
5. **Lowest priority**: `player_enrichment_queue` → mastery + `entries/by-puuid` rank. Only when levels 1–4 have nothing ready.

Also, at least hourly: Data Dragon check → new patch row + static data ingest (champions, spells, items, runes, summoner spells, per patch); keep only the 2 latest patches. A new patch is collected as soon as its static data is in. Whether it is live on a platform (at least one of its matches stored there) is derived from `matches`, read at startup and at each patch change, then set by the platform's first stored match of the patch (`latest patch is live` log line; `latestPatchLive` in the minute `progress` log); until then the previous patch is still collected there. Then older patch rows are deleted (→ cascades) and orphan non-tracked players are purged in small lock-safe batches (only after a deletion, and at startup); a cleanup failure is logged and retried 5 min later. Every cycle writes a `worker_runs` row; each platform loop upserts `worker_status` (heartbeat every 30 s, `auth_rejected_since` while Riot rejects the key, last error). Structured logs to stdout. **Puuids are never logged**: Riot request paths carry them, so the Riot client (`riot/client.ts`) redacts the request's puuid (raw and URL-encoded) from every error it throws (message and `path`) and every log line it writes; whatever logs or stores a Riot error downstream (`worker_status`, enrichment/daily failures…) never sees one. Graceful shutdown on SIGTERM. Config via env: `RIOT_API_KEY`, `DATABASE_URL`, `PLATFORMS` (default `KR,EUW1,NA1,VN2`), `LOG_LEVEL`, `COLLECT_PREVIOUS_PATCH` (`true` keeps collecting the previous patch after the latest is live, for a backfill by hand; default off).

## API

Bun + Hono, port `3000`. Read-only on match data. Owns the stats layer: materialized views (added as migrations in `packages/db`) refreshed by the API on a timer (`STATS_REFRESH_MINUTES`, hourly) when new matches arrived (`REFRESH MATERIALIZED VIEW CONCURRENTLY`; an advisory lock keeps instances from overlapping). There is no on-demand refresh. In-memory response cache (TTL ≈ 10 min) and a per-IP token bucket. Contract types live in `@pick-league/shared` (`api-contract.ts`).

**Behind a gateway.** The API is only called by the web app's server (Next.js on Vercel, which also proxies the desktop app's calls), over HTTPS through Caddy. No browser calls it, so there is **no CORS**.
- `API_TOKEN` (optional env). When set, every route except `GET /health` requires `Authorization: Bearer <API_TOKEN>` (constant-time comparison); otherwise `401 UNAUTHORIZED` with the usual error body. Unset (local dev): no auth.
- Client IP for the per-IP rate limit (and the request log): with a valid token, the visitor's IP the gateway sends in `X-Client-IP` (the socket's when the header is absent); without a token, the socket's, or the first `X-Forwarded-For` address with `TRUST_PROXY`. `X-Client-IP` is ignored on requests without the valid token.

Endpoints (v1):

- `GET /health` → `{ ok, db, latestPatch, matchCount, patchMatchCount }`: `latestPatch` is the patch the stats are served from (the newest kept patch with matches in the refreshed stats, see `stats_patch_matches`; the newest kept patch while none has any), `patchMatchCount` the matches stored on it. If the stats view cannot be read it falls back to the newest kept patch rather than failing.
- `GET /stats/status` → stats freshness `{ refreshing, lastRefreshedAt, lastRefreshDurationMs, matchesIncluded, matchesStored, pendingMatches }` plus `collection: { state, platforms }` read from `worker_status` (one cheap query, the desktop polls every 60 s): per platform `{ platform, heartbeatAt, authRejectedSince, lastError, lastErrorAt, lastMatchStoredAt }` (`lastMatchStoredAt` = newest `matches.fetched_at` of the platform; `lastError` is the worker's text with anything shaped like a player id replaced by `<redacted>` and cut to 300 characters, since this endpoint is public through the gateway); `state` is `key_rejected` when any platform has `auth_rejected_since`, else `stalled` when no platform heartbeated in the last 3 minutes (worker down; database clock), `unknown` without rows (worker never ran or predates 0009), else `collecting`.
- `GET /patches` → kept patches with match counts per platform.
- `GET /static/:patch` → champions (id, slug, name, tags, spells), items, runes, summoner spells — what the desktop needs to render icons/names. Image URLs are Data Dragon CDN URLs. `latest` here is the newest ingested patch (a new champion's name and icon exist before its first match), while `patch=latest` for the stats (tier list, recommendations) is the patch the stats are served from, as in `/health`.
- `POST /recommendations/picks` — body: `{ role, allies: [{championId|null, role}], enemies: [championId|null], bans: number[], availableChampionIds?: number[], masteries?: [{ championId, points }] }` → ranked candidates `{ championId, score, confidence, patchesUsed, reasons: Reason[] }`. When an enemy is (guessed to be) the lane opponent, each candidate gets a `lane_phase` reason at 10 min right after that matchup reason (see Engine, lane phase). When `masteries` (the user's own mastery points, at most 400) is present, each candidate gets a `mastery` reason whose delta is added to its score (a champion not listed counts as 0 points); absent, nothing changes.
- `POST /recommendations/build` — body: `{ championId, role, allies: [{championId, role}], enemies: [{championId, role|null}] }` → `{ patchesUsed, items: { starting, early, core, situational, questUpgrade? }, runes, summonerSpells, skillOrder }` (`questUpgrade`: supports only, the support quest upgrade to pick), every piece with `reasons: Reason[]`. Optional `lanePhase: Reason[]`: `lane_phase` reasons at 10 then 15 min for the locked champion vs the primary lane opponent (the one the build adapts to), each only with enough matchups; absent without a lane opponent.
- `POST /recommendations/draft` — body: `{ allies: [{championId, role|null}], enemies: [{championId, role|null}], side: 'blue'|'red'|null }` (a draft in any state, the probability is the allies') → `{ patch, patchesUsed, winProbability, reasons: Reason[], damage: { allies, enemies }, gameLength: { allies, enemies } }`. See Engine, draft evaluation. `damage` per team: `{ physical, magic, true, champions: [{ championId, physical, magic, true }] }`, each champion's average damage to champions per minute (`stats_champion_traits`, all roles) split by type. `gameLength` per team: `{ early, late, champions }`, the sum of the early / late deltas of its champions in their given or guessed roles (see Engine, game length; `champions` = those with a profile); it never changes `winProbability`. Used by the draft planner and by champion select (in game too).
- `GET /tierlist?role=UTILITY&patch=latest` → `{ role, patch, filters, roleGames, entries }`: every champion of the role with ≥ `minCandidateGames`, scored by its win-rate delta vs the role average (shrunk like the picks engine), tiered S–D by score percentile (non-positive scores capped at B), with win/pick/ban rates (pick rate = share of matches where the champion is picked in the role: its games over half the role's games), confidence, `patchesUsed` (per champion: the previous patch is added below the threshold). Ban rates come from the `stats_champion_bans` / `stats_patch_matches` views. Kept light (~15 KB per role): relations come from the next endpoint.
  - **Filters** `platform=ALL|KR|EUW1|NA1|VN2` (default `ALL`) and `rank=MASTER|GRANDMASTER|CHALLENGER` (default `MASTER` = "Master+"), echoed as `filters` in the response; the cache key includes them. Everything else (per-champion patch choice, percentile tiers, pick rate, `roleGames`) is computed the same way on the filtered rows.
    - Server: only matches of that platform (`matches.platform`).
    - Rank: applied per counted participant, on the player's **current** solo tier (`players.solo_tier` when the stats are refreshed — from the ladders for tracked players, from enrichment for the others — not the tier at match time). `GRANDMASTER` keeps participants whose player is Grandmaster or Challenger, `CHALLENGER` only Challenger ones. A matchup/duo row counts when the champion's own player qualifies (the opponent's/partner's rank is not looked at). `MASTER` (shown as "Master+") counts every participant of the stored matches, which are the matches of Master+ lobbies: each was listed from a tracked Master+ ladder player, but now that every Master player is tracked about 1 counted participant in 6 is currently below Master (16.8 % on 16.22, Nov 2026: Diamond 14.9 %, Emerald 1.6 %, lower 0.3 %; unknown rank 0.03 %). They stay in the default view so it is the full sample; they are excluded by the two other rank filters.
    - Ban rate under filters: `(counted participants whose match banned the champion) / (counted participants)` — the share of the counted players' matches where it was banned, a match weighing once per counted player in it. With every participant counted (server filter only) that is exactly banned matches / matches of that server.
    - Default filters read the unfiltered views (same response as without filters). Other filters read `stats_tierlist_*` views (`0006_tierlist_filters.sql`), kept per (patch, platform, rank level) and summed at request time; they only hold lane-opponent and duo-partner pairs, which keeps them about the size of `stats_champion_vs` (all ally pairs would be ~3.4× bigger).
- `GET /tierlist/champion?role=UTILITY&championId=111&patch=latest` (same query as `/tierlist`, filters included, plus the champion) → `{ role, patch, filters, championId, patchesUsed, games, winRate, matchups, duos, synergies, gameLength? }`: fetched when a champion is selected in the tier list. Every lane opponent (`matchups`), duo partner (`duos`) and ally in the other roles (`synergies`) with ≥ `tierList.minRelationGames` (5) on the champion's `patchesUsed` (summed), as `{ championId, role, delta, winRate, games, confidence }` (confidence = n / (n + k) with the picks engine's `confidenceK.matchup` / `duo` / `pair`), sorted by shrunk delta (best first, worst last). Matchups also carry `lane` (lane-phase difference at 10 min, see Engine) when the sample allows and no server/rank filter is active. Inline in `/tierlist` this would be ~1 MB per role. With server/rank filters, matchups and duos come from the filtered views and `synergies` is `null` (the filtered views have no other-ally pairs). `gameLength` (`{ early, late, earlyGames, lateGames }`, see Engine, game length) is omitted with server/rank filters or when neither delta has enough games.

Requests: POST bodies are capped at 64 KB (`413 PAYLOAD_TOO_LARGE`), `availableChampionIds` at 1000 ids, `masteries` at 400, the other lists at a team's size. A requested champion (`championId` of a build or of `/tierlist/champion`) that is unknown — including ids beyond the `smallint` id columns — gives `404`; ids inside lists that match no champion are ignored (the League client may send ids beyond that range). The response cache stores a computed response only if no stats refresh cleared the cache meanwhile, runs one computation per cache key at a time, and is cleared after every refresh, including one that failed after refreshing some views.

`Reason = { kind: 'matchup'|'duo'|'vs_comp'|'with_comp'|'base'|'item_swap'|'lane_phase'|'mastery'|..., label: string (human readable), delta: number (win-rate delta, e.g. +0.028), games: number, lane?: { minute: 10|15, gold, xp, cs, duo, games } }`.

### Engine (inside the API)

- **Picks** — for each candidate champion in the requested role, an estimate of its win-rate difference, summed from shrunk deltas (every weight 1, `engine/config.ts`):
  1. its own strength: win rate in the role vs the role average,
  2. lane matchup (vs. the enemy in the same role, or all known enemies weighted by role probability if roles unknown; bot lane: both enemy bot laners),
  3. duo synergy (UTILITY↔BOTTOM, MIDDLE↔JUNGLE, TOP↔JUNGLE) and the other allies and enemies pairwise,
  4. vs. enemy / with ally composition traits,
  5. the player's own mastery of the candidate, only when the request carries `masteries`: from `stats_champion_mastery` (`0018_mastery_curve.sql`), the win rate of players in the same mastery bucket (edges 5k / 20k / 50k / 100k / 200k / 500k points) compared with the champion's average — the curve of all champions, plus the champion's own deviation from it shrunk with k = 1,000 (the low-vs-high mastery gap really differs between champions). On 16.22: −9.2 points under 5k … +1.5 from 500k; added as is (weight 1, `ENGINE_CONFIG.mastery`): a held-out fit put its weight at 1.04 and it explained 2.4× as much of the outcome. It takes no part in the confidence.
  A pair delta is the candidate's win rate vs/with that champion minus its own baseline, **minus what the role usually gets vs/with that champion** (games-weighted over every candidate): an enemy's own strength is the same for every candidate and must not favour the ones with small samples. Each delta is shrunk toward 0 (`delta * n / (n + k)`) with a `k` measured on the data: base 250, lane 600, other bot laner 1,600, duo 4,000, other allies 10,000, other enemies 3,500, composition traits 3,000. On 16.22 (~300k matches) the champion's own strength is the largest real effect (±3.3 points), lane matchups ±1.4, duos ±1.1; enemy composition traits had no measurable effect. The `k` of each pair kind is the one at which its held-out weight is 1 (statistics from 80 % of the matches, scored on the other 20 %; `apps/api/scripts/calibrate.ts` re-measures them), and the summed score has a held-out slope of 0.98 ± 0.04. Reasons are listed lane > duo > mastery > comp > base. Exclude banned and already-picked champions; if `availableChampionIds` is given, restrict to them. Confidence derives from sample sizes.
- **Composition traits** come from the data, not hand-written lists: per champion, average physical/magic/true damage share, damage taken + mitigated (tankiness), CC time, healing, plus Data Dragon tags and attack range. Team traits = aggregates of its 5 (or known) champions bucketed (e.g. "AD-heavy", "high CC", "high healing", "tanky", "poke/ranged").
- **Builds** — layered: (1) base = most successful choice for champion+role, scored by shrunk win-rate delta + a popularity bonus, **compared with the other choices of its kind** (the games where it exists: a 3-item path only among games with 3 completed items) with a `k` per kind measured on the data (keystone 700, spells 800, starter 1,200, boots 300, skills 300–450, items 200; quest upgrades and primary minor runes show no measurable difference, so popularity decides). Rune pages are built step by step among the pages of the chosen keystone (secondary tree + its runes, each minor rune, each shard), and the first three items one at a time (first, then second after it, then third): whole pages and paths are too fragmented (the most successful whole page used to be one seen in a few dozen games). Starter, boots, core completed with the most built items (from `item_events` replayed with UNDO handling, ignoring consumables/trinkets/components); (2) adjusted for the lane opponent, (3) item swaps driven by enemy traits with data-backed deltas where samples allow, else Data Dragon item tags (anti-heal vs healing, armor vs AD-heavy, MR vs AP-heavy, tenacity/QSS vs CC, armor pen vs tanky), (4) situational items also answer the own team: the duo partner(s) (`stats_choice_duos`, reason `duo` with the partner in `championIds`) and active ally composition traits (`stats_choice_ally_traits`, reason `with_comp`), data-backed only (no tag rules); every context (lane opponent, enemy traits, duo partners, ally traits) is ranked by its best swap's delta before the situational cap, so an item answering several goes to the one it helps most, and a core item doing notably better with the duo partner or an ally trait gets that reason too. **An item's delta compares its builders with the players who got as far into their build** (kind `items_done`, `0015_items_done.sql`: players with at least its usual slot of completed items, interpolated), in the context and overall: compared with every game, late items looked several points better just because games where players complete more items are won more. Same layering for runes (keystone), summoner spells, skill order (first 3 levels + max order). Each choice carries reasons.
- **Lane phase** — `stats_champion_lane_phase` (`0010_lane_phase.sql`) reads the per-minute frames of `participants`: per (patch, role, champion, lane opponent) the average total gold / XP / CS difference at 10 and 15 min (each with its own matchup count: shorter matches have no 15-minute frame). Top, jungle and mid compare the two players (1v1); the bot lane compares the 2v2 (own + duo partner vs both enemy bot laners), since support gold alone says little. It produces `lane_phase` reasons that **explain and never score**: `delta` 0, `games` = matchups, numbers in `lane`. Patches are combined like the rest (`patchesUsed`, sums weighted by matchups), each average is shrunk toward 0 with `x * n / (n + k)` (`lanePhase.shrinkK` = 20 in `config.ts`: the per-match spread of a 10-minute gold difference is much smaller relative to matchup effects than a win/loss) and it is only shown from `lanePhase.minGames` (20) matchups. Unfiltered data only.
- **Game length** — `stats_champion_game_length` (`0019_game_length.sql`): games and wins per (patch, role, champion) in three buckets of `matches.duration_s`: under 25 min, 25 to under 32 min, 32 min or more. A champion's `early` (resp. `late`) delta is its win rate in games under 25 min (resp. of 32 min or more) minus its overall win rate, minus the same difference for the whole role, shrunk toward 0 with `x * n / (n + k)` on the effective sample of "the bucket vs the champion's other games", n = 1 / (1 / n_bucket + 1 / n_other) (`gameLength.shrinkK` = 300); null under `gameLength.minGames` (100) games in the bucket. The current and previous patches are summed (independent of the per-champion patch choice). A team's profile is the sum of its champions' deltas. It **explains and never scores**: tier list champion details and the draft evaluation only. Unfiltered data only.
- **Draft evaluation** (`engine/draft.ts`) — the picks engine's deltas summed per team: P(allies win) = 0.5 + side edge + (Σ allies' strength − Σ enemies' strength) + (Σ ally–enemy pairs + Σ ally pairs − Σ enemy pairs), clamped to 5–95 %. A champion's strength is its shrunk win rate in its role vs the role average; each pair counts once, averaged over both points of view (ally–enemy: (a vs e − e vs a) / 2; teammates: (a with b + b with a) / 2), each delta centered and shrunk as in the picks engine. Unknown roles are guessed (`assignRoles`) and weighted by their probability; champions not picked yet count as average. The side edge comes from `stats_side_wins` (`0016_side_wins.sql`; blue won 48.5 % on 16.22). The weights (`ENGINE_CONFIG.draft`, `baseWeight` / `pairWeight`) are 1: with the picks engine's `k` the summed score is calibrated on held-out matches (slope 0.98 ± 0.04 on 16.22). Reasons (`base`, `matchup`, `duo` / `with_comp`, `side`) are sorted by |delta|, from the allies' point of view.
- **Patch fallback** — use the current patch alone when the champion+role has ≥ a threshold of games (configurable, e.g. 150), else the current and previous patches combined (their games and wins summed); `patchesUsed` (newest first) is returned and shown.

## Desktop helper

Electron (via electron-vite) + React + TypeScript. UI with shadcn/ui on Base UI, initialised **exactly** with `bunx --bun shadcn@latest init --preset b5Ku0GIBG --pointer`; components are added only through the shadcn CLI.

- **Shared UI** (`packages/ui`, `@pick-league/ui`, shadcn monorepo layout): the shadcn components (`components/ui/*`), the views a web app shows too (tier list, draft planner, build view, stats freshness / collection banner, reasons…), their hooks, the pure logic (`lib/draft.ts`, formatting, confidence…) and the theme (`styles/globals.css`: Tailwind, tokens, fonts, base styles, `@source` of the package). Imports are `@pick-league/ui/components/*`, `/lib/*`, `/hooks/*`, `/styles/*` (also inside the package); components with hooks or events start with `'use client'`. The views never touch `window.pickleague` nor the desktop's `AppState`: their API calls come from a `PickLeagueDataProvider` (`PickLeagueData`: tier list, tier list champion, generic build, draft picks / build / evaluation; plain serializable arguments and `ApiResult` answers — the desktop passes its IPC bridge, a web app its Server Actions) and the rest from props (static lookup, data key, and the League-client-only mastery / owned champions, hidden when absent). Viewer choices (tier list filters, minimum confidence, competitive draft) live in the browser's local storage. `shadcn add` from `apps/desktop` puts new components in the package (`components.json` aliases); champion select, settings, header and window chrome stay in the desktop.

- **LCU connection** (main process): find the running `LeagueClientUx` process and read `--app-port` / `--remoting-auth-token` from its command line (Windows: PowerShell `Get-CimInstance Win32_Process`; macOS/Linux: `ps`), falling back to the `lockfile` in the install dir. HTTPS with Riot's self-signed cert (trust it for `127.0.0.1` only), basic auth `riot:<token>`. Subscribe over WebSocket (WAMP, `OnJsonApiEvent_lol-champ-select_v1_session` and `OnJsonApiEvent_lol-gameflow_v1_gameflow-phase`). Reconnect when the client restarts (a WebSocket upgrade left unanswered gives up after 10 s and is retried).
- **Reads**: `/lol-champ-select/v1/session` (picks, bans, assigned positions, actions), `/lol-champions/v1/owned-champions-minimal`, `/lol-champion-mastery/v1/local-player/champion-mastery`, `/lol-summoner/v1/current-summoner`, `/lol-gameflow/v1/gameflow-phase` (a champion select that ends into a game stays shown, with its build, until the game ends — also while the client is closed during the game, until a reconnected client reports a phase outside the game or a new champion select), `/lol-gameflow/v1/session` (teams of a game already in progress when the app starts; player ids matched against the user's own to find their team, never sent anywhere).
- **Writes (only these)**: rune page + summoner spells, **automatically when the local player locks in** (setting, on by default, can be switched off; also a manual "Apply" button). Rune page: create/replace one page named `PickLeague` via `/lol-perks/v1/pages`; if no slot is free and no `PickLeague` page exists, warn instead of deleting a user page. Spells: `PATCH /lol-champ-select/v1/session/my-selection` putting Flash on the key chosen in settings (D or F, F by default); a pair without Flash keeps the user's keys. **Never** pick, ban, lock in, accept, or reveal hidden player identities.
- **UI**: champion select view (allies/enemies/bans, my role), recommended picks with mastery badge on each champion icon and expandable reasons, ranked for the user's mastery: the picks request carries the user's mastery points per champion (points only: no Riot ID, no puuid; setting "Rank picks for my mastery", on by default; the draft planner and the web app do not send them); build view (lane phase vs the lane opponent, items in buy order, situational items, runes, spells, skill order) with reasons on every element; lane-phase reasons shown as figures ("−420 gold · −8 CS · −310 XP at 10 min", "2v2" for the bot lane) and tier list matchups with their lane gold at 10 min ("+250g @10", CS / XP / sample on hover); tier list champion details show its early / late game deltas ("Early game +2.4%", "Late game −1.8%", games under 25 min / of 32 min or more); patch used + sample size; draft planner (works without the League client): a draft played by hand, ranked solo/duo by default — 10 bans alternating Blue/Red (skippable), then picks B1 R1 R2 B2 B3 R3 R4 B4 B5 R5 — or competitive ("Competitive" switch, remembered; changing it starts a new draft): 3 bans each (B R B R B R), picks B1 R1 R2 B2 B3 R3, 2 bans each (R B R B), picks R4 B4 B5 R5; each pick for a role the user chooses (the team's first open role by default). Flex picks: a role the team already has can be chosen for the pick (the champion there moves to the first open role, said before picking), and any picked champion can be moved to another role of its team at any time (⇄ next to it, swapping with the champion there; not a turn, Undo does not revert it). A **win chance** bar (blue vs red, reasons on hover or focus) and each team's **damage split** (AD / AP / true bar, per-champion figures on hover) with its **game length** line under it ("Stronger early (+2.4%) — falls off late (-1.8%)") follow the draft (`POST /recommendations/draft`; a competitive draft sends `side: null`, since the side edge comes from ranked matchmaking — which side gets the stronger players — and not from the draft), plus a takeaway under the win chance when one team clearly outscales ("Blue outscales: Red wants a short game"; in champion select "You outscale: play for late" / "They outscale: end early"); champion select shows the same for the user's team (side from the LCU `team`, hovered champions included), also in game. The planner shows with the remaining champions ranked by `POST /recommendations/picks` for the team and role on turn (the team's other roles as allies, the other team's picks as enemies, every ban; `limit` 100; champions without a candidate shown after, dimmed) and, for any drafted champion, `POST /recommendations/build` with its teammates and the enemies, all with their roles; turn order and request bodies live in the pure `lib/draft.ts` of `@pick-league/ui`, the calls go through the main process (`draftPicks` / `draftBuild` IPC, bodies validated with the contract's zod schemas), debounced and cached per request in the renderer; keyboard: Ctrl/Cmd+K (or F) focuses the search, Tab or ↓ from it goes to the first champion of the list, arrows / Home / End move between champions (one tab stop per list, roving tabindex: grid in the planner, rows in the tier list and the champion select picks; PageUp / PageDown in lists), Enter takes the first match from the search; header with stats freshness (`GET /stats/status`, polled every 60 s) and a warning + line under the header when collection stopped (`collection.state` `key_rejected` or `stalled`, with the time since: stopped on the server, stats may be getting stale, nothing for the user to do); settings (API URL default `https://pick-league.vercel.app/api/v1`, the public gateway that forwards the API's paths and bodies; `PICKLEAGUE_API_URL` or the field overrides it, e.g. `http://localhost:3000` in dev; auto-apply toggle). Dark mode friendly. Icons from Data Dragon CDN.

## Web app

Next.js (App Router) in `apps/web`, deployed on Vercel (root directory `apps/web`). Same shared views and theme as the desktop (`@pick-league/ui`, shadcn components added only through the CLI, `components.json` aliases into the package), minus what needs the League client (champion select, auto-apply, mastery / owned champions, settings, window controls). Routes: `/` tier list, `/draft` draft planner; the root layout renders the header (API patch + matches, stats freshness, collection banner), the navigation (left rail, bottom bar on phones) and both views, kept mounted across routes like the desktop. The views render in the browser only (they read local storage and the platform on their first render).

- **Data**: `lib/api.ts` (`server-only`) calls `API_URL` with `Authorization: Bearer <API_TOKEN>` and the visitor's IP in `X-Client-IP` (first `X-Forwarded-For` address, else `X-Real-IP`; Vercel sets them). GETs use the data cache (`next.revalidate`, `lib/cache.ts`: static data 6 h, patches 1 h, tier list / champion 10 min, health and stats status 60 s; the cache key includes the headers, so answers are reused per visitor IP); POSTs are never cached. The root layout (Server Component) fetches static data, the header status and the first tier list; the views' `PickLeagueData` comes from Server Actions (`app/actions.ts`, arguments validated with the contract's zod schemas, answers are plain `ApiResult`s); the header status is polled every 60 s through a Server Action.
- **Gateway** (`app/api/v1/[...path]/route.ts`, `lib/gateway.ts`): forwards only the contract routes (`GET` health, patches, static/:patch, tierlist, tierlist/champion, stats/status; `POST` recommendations/picks|build|draft) with the token and the caller's IP, passing through status, `Retry-After` and the JSON body; other paths are `404 NOT_FOUND`, POST bodies over `MAX_REQUEST_BODY_BYTES` are `413`. Successful GETs carry `Cache-Control: s-maxage` (same lifetimes) for the CDN; POSTs and errors are `no-store`.
- **Env** (server-only): `API_URL`, `API_TOKEN` (`apps/web/.env.example`).

## Docker

- `docker-compose.yml` at the root: `postgres` (postgres:17, named volume, healthcheck, tuned for 12 GB: `shared_buffers` 3 GB, 1 GB `/dev/shm` for parallel queries), `worker`, `api` (published on `127.0.0.1:3000` only), `caddy` (ports 80/443, TLS for `PUBLIC_HOST`: a Let's Encrypt IP certificate on the short-lived profile when it is a bare IP, `deploy/Caddyfile`). Each service has a memory/CPU limit (Postgres 7 GB, API 1 GB, worker 512 MB, Caddy 256 MB). Images built from a single multi-stage `Dockerfile` using `oven/bun`. `restart: unless-stopped`, logs rotated (3 × 10 MB per container), `api` healthcheck on `/health`. `.env` provides `RIOT_API_KEY` (+ `POSTGRES_PASSWORD`, `PUBLIC_HOST`, `API_TOKEN`, `TRUST_PROXY`, optional `PLATFORMS` and API settings): only the worker receives the whole file, the API gets its own settings listed in the compose file, never the Riot key.
- `deploy/`: Caddyfile, and systemd timers installed by `deploy/install.sh`: nightly `pg_dump` (directory format, zstd, last 3 kept), a watchdog every 2 min (restarts a stopped/unhealthy service, or the worker when its `worker_status` heartbeat is over 5 min old), and a 5-minute sample of the worker's open HTTPS sockets.
- `docker-compose.override.example.yml` (publishes Postgres on 127.0.0.1:5432) and the `bun run dev:*` scripts let each app run outside Docker against the dockerised Postgres.
- `.github/workflows/desktop-release.yml`: a `desktop-v*` tag builds the Windows installer and attaches it to a GitHub release.
