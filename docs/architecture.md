# PickLeague — Architecture (v1)

PickLeague helps a player (a support main first, but every role is covered) pick the right champion in League of Legends champion select and then build it: items + buy order, runes, summoner spells, skill order — all adapted to the 9 other champions, **always showing the reasons** behind every recommendation.

Data comes from high-elo ranked solo/duo games (Challenger + Grandmaster + Master players of KR, EUW1, NA1, VN2, tracked from the top of the ladder down; then the Masters outside Riot's list, and optionally as many of the best Diamond players as the remaining Riot budget allows). The latest patch is collected, and on each platform the previous one too until that platform's first match of the latest patch is stored; the previous patch then stays in the database until the next one replaces it.

The server side (Postgres, worker, API, Caddy) runs with `docker compose up -d` on a Linux VPS. The web app runs on Vercel and is the only caller of the API; the desktop app runs on the player's computer (it must reach the local League client) and calls the API through the web app's gateway, so the VPS address is never handed out.

## Tooling

- Bun ≥ 1.3 workspaces (`packages/*`, `apps/*`), TypeScript strict, Biome, `bun test`.
- Root scripts: `check` (biome), `typecheck` (tsc -b or per package), `test`.
- Postgres client: `postgres` (porsager). No ORM; migrations are plain `.sql` files in `packages/db/migrations/NNNN_name.sql`, applied in order by a small runner that records them in `schema_migrations`. Migrations run automatically when the worker and the API start (idempotent, guarded by an advisory lock).

## Riot API facts the worker relies on

- **Hosts.** Platform host `https://{platform}.api.riotgames.com` (`kr`, `euw1`, `na1`, `vn2`) for league-v4, champion-mastery-v4. Regional host `https://{cluster}.api.riotgames.com` for match-v5. Match clusters: KR→`asia`, EUW1→`europe`, NA1→`americas`, VN2→`sea`.
- **Rate limits are enforced per host (routing value).** App limit (this key): 20 req / 1 s and 100 req / 2 min per host. Method limits also exist per endpoint. Read the real limits from `X-App-Rate-Limit`, `X-Method-Rate-Limit` (+ `-Count`) response headers rather than hardcoding; on `429` honour `Retry-After`. One limiter per host, so the 4 platforms + 4 clusters progress independently.
- **Never use a second API key** to go faster (Riot policy).
- Endpoints:
  - `GET /lol/league/v4/challengerleagues/by-queue/RANKED_SOLO_5x5`, `.../grandmasterleagues/...`, `.../masterleagues/...` (every Master player: the worker keeps the top ones by LP) → entries with `puuid`, `leaguePoints`, `wins`, `losses`.
  - `GET /lol/league/v4/entries/RANKED_SOLO_5x5/DIAMOND/{I|II|III|IV}?page={n}` (n from 1, platform host; only with `DIAMOND_MAX_TRACKED`) → an array of up to 205 entries (`puuid`, `tier`, `rank`, `leaguePoints`, `wins`, `losses`, `inactive`…) in no particular order, empty after the last page. A division is hundreds of pages (Nov 2026: KR I 107 / II 238 / III 97 / IV 251 pages, 141,600 players; NA1 46 / 99 / 50 / 119; VN2 38 / 76 / 33 / 80), so reading all four takes a platform host minutes at its app limit (KR: about 14), during which players move between pages. The Master list cannot be extended this way: every endpoint stops at 10,000.
  - `GET /lol/league/v4/entries/by-puuid/{puuid}` (platform host) → the solo queue entry of any player: `tier`, `rank`, `leaguePoints`, `wins`, `losses`. Used for the rank of enrichment, and as the check of the Masters outside Riot's list: their `wins + losses` is the same counter as on the ladder lists.
  - `GET /lol/champion-mastery/v4/champion-masteries/by-puuid/{puuid}` (every champion of the player: only those with a stored game are kept).
  - `GET /lol/match/v5/matches/by-puuid/{puuid}/ids?queue=420&type=ranked&startTime={epochSeconds}&count=100`.
  - `GET /lol/match/v5/matches/{matchId}` and `.../{matchId}/timeline`.
- **Patch.** Data Dragon `https://ddragon.leagueoflegends.com/api/versions.json`, first entry is latest (`15.22.1`). A match's `info.gameVersion` (`15.22.715.1234`) belongs to patch `major.minor`. Data Dragon may lag the live patch by hours: a match from a patch newer than Data Dragon stays `PENDING` and is retried later. It may also be about a day *ahead* of the live servers (a patch published before any server plays it): each platform then keeps collecting the previous patch until it has stored a match of the new one, and the API keeps serving the previous patch until the stats have matches of the new one.

## Worker

Long-running Bun process. Each platform runs its own loop; work is pulled from priority levels, highest first, as long as rate-limit budget allows. Each platform has two budgets of 3,000 requests an hour: the regional host's (match ids, matches, timelines), which limits collection and is used at about 95 %, and the platform host's (ladder lists, Diamond pages, the checks of the Masters outside Riot's list, masteries, rank lookups), which is used in full too.

**The platform host serves, in this order**: (1) the three ladder lists (priority 5; 3 requests an hour, 3 more each time more Master players are tracked); (2) the pages of the Diamond sweep (4; once an hour: 693 pages on KR, 762 on EUW1, about 315 on NA1 and 230 on VN2 in Nov 2026); (3) the mastery refresh of tracked players (2; about 210 an hour for 15,000 tracked players at 3 days, plus the first games on a champion: level 4); (4) enrichment (1; one or two requests a player: level 5); (5) the checks of the Masters outside Riot's list (0; one request a player, at most `OUTSIDE_MASTER_CHECKS_PER_HOUR`, 1,500 by default: level 6). The first two decide who played for hundreds of players a request and are a fixed number of requests, far under the host's limit: they always get through, whatever waits below them. Masteries and ranks come next because **the stats of the stored games read them**: the mastery curve only counts a participant with a mastery row for the champion played (fetched before the game since 0035: a row fetched after it counts for the player's later games), and the Master+ / Grandmaster+ / Challenger filters a participant with a known rank. Until 2026-11-25 the checks came before them, capped so they left those two about 800 requests an hour on KR; enrichment then fell behind on every platform (63,500 players waiting on KR, growing 17,000 a day) and 12.5 % of the participants of patch 16.23 had no mastery for their champion (15 % on KR and EUW1), all of them waiting in that queue. The checks only decide *when* an outside Master is listed, and a late check loses nothing (their listing starts where the last one stopped), so they now get what the others leave, still at most their ceiling: none while enrichment works through a backlog, then a slower rotation. The allowance of the checks fills at the hourly rate and holds half an hour's worth. Enrichment is served oldest first (a stored Diamond lobby brings up to 9 new players).

**The regional budget is spent in three strict tiers**, per platform:

- **Tier 1, the tracked apex players** (Challenger, Grandmaster, Riot's Master list): the listings of those who played (level 2) and their matches (level 3). *Caught up* = no apex listing waiting or running (players cooling down after a failed listing aside) and at most 50 PENDING matches in the apex band of `fetch_rank` (`expandBelowPendingMatches`). Nothing of the tiers below is looked at, nor the retried and deferred matches at the back of the queue.
- **Tier 2, the Masters outside Riot's list** (level 6): the listings of those whose `wins + losses` moved since their last check, and the fetch of the games those listings find. The checks themselves run on the platform host and cost this budget nothing. Their listings run when every Master of Riot's list is tracked and tier 1 has caught up; they never wait for a Diamond listing or a Diamond match. *Nothing waiting* = no outside Master is waiting for a listing (and could be listed: a player whose listing failed waits 1 h and does not count), none of their listings is running, and at most 50 PENDING matches are left in the apex and outside-Master bands together. A match that fails or is deferred moves to the back of the queue at once (out of these bands; `FAILED` after 2, 5 or 10 tries), so a match that cannot be fetched never keeps tier 2 open.
- **Tier 3, the tracked Diamond players** (level 1, Diamond): neither their listings nor their matches start unless tier 1 has caught up and tier 2 has nothing waiting. Two sub-tiers, in strict order as well: **3a**, the Diamond players (any division) seen in a Master+ game in the last 7 days; **3b**, the other tracked Diamond I players, whose listings and matches only start when 3a has nothing waiting (no 3a listing waiting or running, players cooling down after a failed listing aside, and at most 50 PENDING matches in the 3a band). How many are tracked is a target the worker sizes by itself (below).

A tier is held back twice. Its work is not handed out before its turn: a listing loop does not pick a Diamond player and a match loop does not take a Diamond match, nor those of a Diamond I player of 3b while 3a has something waiting (checked again for each one; the queue is read again when a listing queues new ids), so the loops stay free for the tiers above. And its requests wait behind those of the tiers above in the regional limiter: apex listings (priority 4), apex matches and every timeline (3), outside Masters' matches (0), their listings (−1), 3a listings (−2), 3a matches (−3), 3b listings (−4), 3b matches (−5). Only the first request of a match takes its tier's priority: once granted, the match is finished with its timeline at priority 3, so a match loop holds a lower-tier request for a short time only (at most 3 such requests, the match loops, can be waiting when a tier above gets work; they are granted as soon as no request of a tier above is waiting). `fetch_rank` has one band per tier, claimed in that order: an apex player's ladder position (< 100,000), 100,000 for a match listed by an outside Master, 200,000 + the position among the tracked Diamond players of 3a, 400,000 + the position among those of 3b, 1,000,000 for retried and deferred matches (the back of the queue: anyone's, fetched at priority 3 after everything that is claimable, never held back with the Diamond bands). A match listed by players of several tiers keeps the best rank.

Who starves whom: tier 1 is never delayed by the others beyond those few in-flight requests. Tier 2 only yields to tier 1, and is bounded: a player is listed at most once per check that saw their counter move, and with the skip rule only when their new games are not stored already. Tier 3 gets what the two others leave; if they take the whole day it gets nothing, and its target shrinks accordingly; inside it, 3b gets what 3a leaves. One exception to the order: the search for the patch boundary at startup and after a patch change (level 3) fetches O(log n) queued matches whatever their tier.


1. **Ladder refresh** (once per hour per platform): Challenger + Grandmaster lists, plus the top N of the Master list by LP. N starts at 0 (fresh database) and grows by 500 each time tier 1 has caught up (see above: a Diamond backlog does not delay it; checked every minute; the refresh with the larger N runs right away). After a restart N is the number of Master players in `ladder_entries`. More Master players is the lever for more data, not a longer history. Upsert `players` + `ladder_entries`. Players whose `wins + losses` changed (or are new) are marked "played" (`players.listing_requested_at`, so a restart loses nothing; cleared when a listing that started after it finishes).
   **Diamond players** (`DIAMOND_MAX_TRACKED` > 0 per platform; default 0 = none, and no Diamond request is made): after each hourly refresh the four Diamond divisions are read page by page (platform host, priority 4: after the three apex lists, before everything else of that host). The best candidates are tracked, as many as the **target** of the platform (`diamond_tracking.target`, at most `DIAMOND_MAX_TRACKED`, which is only a ceiling for the disk). One order for every candidate: (1) those seen in a "Master+ game" in the last 7 days (`players.last_seen_with_master_at`: the start of the newest stored match they shared with a player known as Master, Grandmaster or Challenger when it was stored — an apex row in `ladder_entries`, or `players.solo_tier`), whatever their division, by division (I first) then LP: **3a**; (2) then the other Diamond I players by LP: **3b**. Nobody else is a candidate: a Diamond II to IV player who was not seen in a Master+ game is not tracked (one tracked under the previous rule leaves at the first sweep). No group is tracked without condition: the target holds for all. A sweep is up to 140,000 entries, so only those that can end up tracked are kept in memory: the players of group 1, the tracked ones, and of the other Diamond I players the best target + 500 by LP. **Ranks from the sweep**: a page gives the tier, division, LP and counters of 205 players; for those already in `players` (the players of Riot's apex lists aside) they are stored page by page (`players.solo_*`, `rank_refreshed_at` = the time of the page), one statement a page that only writes the rows whose rank changed or whose `rank_refreshed_at` is 12 h old (half of the 24 h of level 5): the hourly cost is the players who played plus a twelfth of the others. Nobody is created. This part is kept even when the sweep fails later (each page is true when it is read), and failing to store it never fails the sweep. It is what lets enrichment skip the rank request (level 5), and it takes a Master outside Riot's list who dropped to Diamond out of that set (level 6). A sweep is applied as a whole: if a page fails, nothing changes (nobody is removed, nobody is taken as "did not play") and the next cycle tries again; a sweep with no player at all is not applied either. A tracked player a complete sweep did not see (moved between pages meanwhile, promoted, decayed) is kept exactly as stored and is dropped once the last sweep that saw them is 24 h old; one who is on Riot's apex lists is left to the apex ladder. Tracked Diamond players have `ladder_entries` rows (tier `DIAMOND` + division), "played" by `wins + losses` (each entry with the time of its own page), listing in the order of their group (3a by division then LP, then 3b by LP; after a restart the two groups are read back from `ladder_entries` and `players.last_seen_with_master_at`), skip rule, mastery refresh; their first listing goes back like any newly tracked player's. Their Diamond-lobby matches mark nobody as seen with a Master+ player, so tracking does not spread by itself. A player who is no longer among the best `target` candidates (the target shrank, others passed them) leaves `ladder_entries` like any player leaving the ladder and is no longer waiting for a listing; their stored matches stay, and their queued ones are still fetched in the Diamond bands.
   **The Diamond target** sizes itself on whether the platform keeps up over a day, recorded one ladder cycle (an hour) at a time. Every minute the ladder loop looks at the cycle in progress: the first time the three tiers have *nothing waiting* (every Master of Riot's list tracked, no listing waiting or running, tier 2 done, at most 50 PENDING matches outside the back of the queue), the cycle is recorded as **kept** (`K`). A cycle that ends without that is **missed** (`M`), unless matches were waiting for patch data (Data Dragon behind the live patch): `W`, neither kept nor missed. Tier 2 has no excuse of its own any more. The daily pass, during which tier 3 could do nothing by design (`P`, and `R` for the hours after it), is gone: the outside Masters' listings are spread over the day and only cover those who played, so an hour in which tiers 1 and 2 left nothing to the Diamond players is an hour the platform did not keep up at this size. (A history written before may still hold `P` and `R`: read as neither.) The outcomes since the target last changed are kept in `diamond_tracking.cycles`. At the start of each cycle, before the refresh and the sweep that applies it: the target **shrinks by a step** (`diamondStep`, 1,000; the last candidates of the order above leave) once 24 cycles (`diamondShrinkMissedCycles`: a full day) were missed since the last kept one, `W` cycles neither counting nor starting the count over; else it **grows by a step**, up to the ceiling. **Sized on the day, not on the hour** (since 2026-11-25): the backlog the evening peak leaves is caught up in the quiet hours. Under the first rule (shrink after 6 missed cycles, grow only after a day without any) the target fitted the peak hour, and the quiet hours went unused: 17-46 % of the regional budget in NA1's and VN2's quiet hours, and KR and EUW1 shrank from 5,000 to 4,000 during their peak although the backlog cleared that night. Nothing is lost by listing a Diamond player hours late (the listing starts where the last one stopped; tiers 1 and 2 still go first). **Fast start**: while the target has never shrunk (`diamond_tracking.shrunk_at`), or not for 7 days, two kept cycles in a row are enough (`diamondFastGrowCycles`; with 5,000 Diamond players NA1 used 35 % of its regional budget on 2026-11-23, and a step a day would take weeks to find what it carries); the first shrink says a day's budget is reached, and from then on it grows when the last 24 cycles (`diamondGrowCycles`: a full day) hold at least 3 kept ones (`diamondGrowMinKeptCycles`: hours in which the three tiers ran out of work, so budget was left; missed cycles in between do not matter; a day spent waiting for patch data proves nothing) and the target is filled. The history starts over at each change, so the next change is decided on cycles that ran at the new size. **No oscillation after a growth step**: the 1,000 new players' first listings go back to the start of the patch, a burst that can take hours; after a step, cycles are not recorded at all until the three tiers have nothing waiting again (for at most 24 cycles that would have been missed ones, `diamondSettleCycles`), so the burst can neither count as missed cycles nor as the kept day of the next step; a step that is still not absorbed after that is undone 24 missed cycles later, and trying again takes a new full day. **Restarts**: the target, the history and the settling are in `diamond_tracking`, written at each recorded cycle (a kept cycle as soon as it is kept). A cycle that starts less than a ladder interval after the last recorded one is the same cycle (restart, or a retried refresh): it can only turn that one into a kept cycle, so restarts neither add kept cycles nor missed ones; a cycle interrupted before it was kept is simply not recorded. After a stop of more than one ladder interval (`worker_status.heartbeat_at`) the backlog of the stop is treated like a growth burst. Without a stored target (the first start with Diamond tracking) the target is the number of Diamond players tracked so far (at most the ceiling), with the same settling for their first listings still waiting. Migration 0032 (the end of the daily pass) starts the history over and gives 48 cycles to settle: during the first rotation every outside Master gets a first check, and during the next one a first real listing when they play (the skip rule has no baseline for them yet), a burst of tier 2 work that says nothing about the size of the target. A target above a lowered ceiling comes down to it. `diamond` in the minute `progress` log: players seen by the last complete sweep per division, `target`, `tracked` (and `trackedWithMaster`, how many of them are of 3a), `cap`, `cycles` (the last 24 at most: `K`, `W`, `M`) and `keptCycles`, `settleCyclesLeft`, `lastChange` (when, from which target, why).
2. **Match id listing** for "played" players, best ladder position first (Challenger by LP, then Grandmaster, then Master; then, only when it is their turn, the Diamond players of 3a by division and LP, then those of 3b by LP), using `startTime = players.matches_synced_until` (first time: start of the current patch as far as we know, else 14 days ago), paginating until exhausted. New ids of the player's own platform go to `match_fetch_queue` with the player's `fetch_rank` (an apex player's ladder position, a Diamond player's position in the band of their sub-tier; a match listed by several players keeps the best one), and the match loops read the queue again. A player who plays again during their listing is listed again; a failed listing is retried after a cooldown (5 min, doubling up to 6 h).
   **Listing skip rule** (`LISTING_SKIP` = `off` (default) | `shadow` | `on`). A stored match holds 5.7–7 tracked players, each listed to find it again: most listings bring nothing new. Per tracked player, `ladder_entries` keeps a baseline set by their last real listing: `listed_games` (their `wins + losses` when it was decided), `listed_snapshot_at` (the ladder refresh that produced those counters, `games_changed_at`) and `listed_at`; an outside Master's is kept the same way in `outside_masters`, on the counters of their checks (level 6). When the player is about to be listed, with `games_now` and `snapshot` the current counters and their refresh: `expected = games_now - listed_games`, `stored` = their stored non-remake matches that ended (`started_at + duration_s`) after `listed_snapshot_at` and at least 15 minutes before `snapshot` (`listingSkipLadderLagMs`: Riot's ladder counts a finished game late — 11 % of the games ended in the 2 minutes before a refresh were in its counters, all of them from 10 minutes, measured on 2026-11-22 — so a recent game may not be one of the new ones); if `expected > 0` and `stored >= expected`, the listing is **skipped**: the request is cleared without calling Riot, and neither `matches_synced_until` nor the baseline moves, so the next real listing covers the whole period and the counts stay cumulative. Always a real listing without a baseline, when the counters went down (season reset) and when `listed_at` is as old as the **safety interval of the player's group** (`listingSkipSafetyMs`): 24 h for the apex players, 72 h for the Masters outside Riot's list and the Diamond players (a game whose loss Riot never counted would otherwise hide a later game for ever; but at 20,000 players and more a forced listing a day each is most of the regional budget, and their counters come from a check of their own or from a full list every hour). A game that ended after the snapshot is not in the counters, so it cannot stand for an older missing one; counting too few only costs a listing. `shadow` evaluates the rule and keeps the baseline exactly as `on` (it does not move on a would-be skip) but every listing runs, and a would-be-skipped listing that queued new ids is recorded in `listing_skip_misses` (not all are misses: a game started after the snapshot is new anyway). The outside Masters of level 6 follow the same rule on the counters of their checks.
   The rule only pays if a listing's matches are stored before the players below are decided, so in `shadow` and `on` a tracked player is only picked for a listing once no PENDING match with a lower `fetch_rank` than their position is left (matches queued by better-placed players; checked again after each fetched match), and a listing that queued ids makes the match loops read the queue again instead of finishing what they had claimed. The request priorities are unchanged (the decision is taken when the player is picked, not when the request is granted, so a limiter priority could not delay it). Nothing can starve: a listing never waits for matches queued by players below it nor for retried or deferred matches (back of the queue); an apex player never waits for a match of tier 2 or 3 (their bands come after every apex position), while a Diamond player waits for the matches of the tiers above too (they are fetched first anyway), so no backlog of those delays it and the top players are listed as soon as they play; what it waits for is being fetched at the head of the queue; and after 5 min it goes ahead anyway. With two listings in flight the second is decided before the first one's matches exist. An outside Master is handed out for a listing the same way: once no PENDING match is left in the apex and outside-Master bands (what the apex players and the outside Masters listed before brought), or after 5 min. A replay of 4 days of production data (before this was built) put the listings saved at 63–66 % with the 24 h rule (76–81 % without it); `shadow` is there to measure it for real. `off` keeps the previous behaviour exactly. `listingsSkipped` (would-be skips in `shadow`) and `listingSkipMisses` in the minute `progress` log.
3. **Match + timeline fetch** from the queue, lowest `fetch_rank` first: apex players' matches, then the outside Masters', then the Diamond players' when it is their turn, 3a before 3b (retried and deferred matches go to the back). Parse, keep only schema fields, insert everything in one transaction (matches, teams, bans, participants with their per-minute gold / XP / CS, one `participant_events` row per participant holding its purchases, sales, undos and skill points as arrays, `players` rows for all 10 players with their Riot ID from the payload). Matches of a patch that is no longer collected (older than the previous one, or the previous one once the latest is live on the platform) → `SKIPPED_OLD_PATCH` before their timeline is fetched; the first one seen bounds every listing (paginating stops there) and every pending id below it is skipped in one statement. After a patch change (and at startup) the backlog is probed by game id (highest pending first, then medians between the old and current bounds), so a stale backlog costs O(log n) requests instead of one each. Errors: transient ones (Riot 429/5xx after the client's retries, network, database connection) defer the match without counting an attempt (`FAILED` after 10) and back the loop off (5 s doubling to 5 min); deterministic ones (404, other 4xx, parse) fail it on the second attempt; anything else on the fifth. Non-ladder players are enqueued into `player_enrichment_queue` (respecting the 7-day rule). **A first game on a champion**: masteries are only kept for champions with a stored game (see level 4), so each player of the match without a mastery row for the champion they played is asked for again in that same transaction — a tracked player by clearing `players.masteries_refreshed_at` (first in line at level 4), the others by queueing them whatever the age of their data. It is asked once per stored match: an answer that still has no row for the champion is stored like any other and nothing asks again because of that match.
4. **Mastery refresh of tracked ladder players**: mastery, if older than 3 days (`MASTERY_REFRESH_DAYS`; it was every day until masteries were only kept for the champions with a stored game: what a refresh brings now is the points of those champions, and a first game on a champion asks again by itself) or never fetched, those cleared by a first game on a champion first (platform host only). Of a mastery answer, only the rows of champions the player has a stored game on are kept (`champion_masteries`, the only ones the stats read: 4 % of what Riot returns); the write waits for a match insert of that player in flight, so a game being stored is seen. Riot IDs are not looked up: they come with each match payload and nothing reads them.
5. **After the mastery refresh, before the checks of level 6** (platform host, above): `player_enrichment_queue` → mastery (kept as at level 4), and the `entries/by-puuid` rank only when the stored rank is missing or older than 24 h (`enrichmentRankFreshMs`): otherwise a ladder, the Diamond sweep (every known Diamond player, kept at most 12 h old), a check of level 6 or a previous enrichment refreshed it, and the player costs one request instead of two (`enrichedRankFresh` in the minute `progress` log counts them). Stored and taken off the queue in one transaction.
6. **Masters outside Riot's list** (tier 2; Riot's Master list stops at 10,000 players, so the bottom of a large Master tier is never on it: 23,000 players on KR and on EUW1, 4,000–5,000 on NA1 and VN2). Riot gives no list for them, but `entries/by-puuid` returns each one's solo queue entry, with the same `wins + losses` counter as the ladder lists, on the platform host. So they are not listed blind (it took a daily pass of one regional request a player, whether they had played or not: 21 h a day on KR): each one's counter is **checked** on the platform host, and only those who played are listed.
   **The set** is the table `outside_masters`: the players whose stored solo rank is Master or above (`players.solo_tier`: from enrichment, or from the ladder they dropped off) and who have no `ladder_entries` row. It is brought in line with those two after each ladder refresh and each Diamond sweep (one scan of the platform's players): a player Riot's list picks up is followed by the ladder from that refresh on (as a player new on the ladder: listed once), one who is ranked lower leaves. A table of its own, because neither alternative keeps the existing paths right. Every reader of `ladder_entries` takes a row for a player on a list that is refreshed as a whole: rows a refresh did not return are removed, `masterTracked` is the number of MASTER rows, every row never listed gets a first listing, has its masteries refreshed and is kept out of enrichment, the DIAMOND rows belong to the sweep, and the rows are the ladder order of `fetch_rank`; none of that holds for a player checked one by one. And on `players`, `solo_wins + solo_losses` are also written by enrichment and by the sweep, so they cannot say what the last *check* saw.
   **The checks** run once every Master of Riot's list is tracked, in rotation: never checked first, then least recently checked (`checked_at`), nobody again within an hour (`outsideCheckIntervalMs`, the pace of the ladder lists), at most `OUTSIDE_MASTER_CHECKS_PER_HOUR` an hour (the platform host, above). They come last on the platform host, after enrichment: at 1,500 an hour a rotation takes about 15.6 h on KR and EUW1, 2.6 h on NA1 and 3.6 h on VN2, longer while enrichment has a backlog. A check stores the player's rank (`players.solo_*`, `rank_refreshed_at`) and compares `wins + losses` with the last check's (`outside_masters.games`). **Unchanged**: only `checked_at` moves, nothing is asked of the regional host. **Moved**: the player played; `players.listing_requested_at` is set (durable, like a tracked player's) and `games_changed_at` becomes the time of this check. **No longer Master or above**, or unranked: the row is removed, with a listing request still waiting; a Diamond player is then a Diamond candidate like any other (the sweep also takes out a Master it sees in Diamond). A check that fails sends the player to the back of the rotation, counter untouched; a 401/403 on a check is that player's failure and does not pause the platform as a rejected key does (the ladder refresh sees a key that is really rejected).
   **First check** (nothing to compare with): when the player's match ids were listed in the last 72 h (the safety interval of the group; `players.matches_synced_until` says when), the counter is simply the starting point and nothing is listed. Nothing is lost: the first real listing starts from `matches_synced_until`, so it covers the games between that listing and the check too; it only waits for the counter to move. A player never listed, or not for 72 h, gets one listing. So the first start of this version costs no burst of listings: the daily pass listed everyone in the last day or two, and the first rotation ends within 16 h.
   **Listings** (tier 2, one at a time, oldest request first): when every Master of Riot's list is tracked and tier 1 has caught up, with the skip rule of level 2 on the baseline kept in `outside_masters` (`listed_games`, `listed_snapshot_at`, `listed_at`), and the 72 h safety interval. The **snapshot** of a counter is the moment the check that first saw it was answered: the clock is read after the response, not when the request was made, which can be minutes earlier (the request waits behind the Diamond sweep). As the end of the window it is at most one request (15 s) later than Riot's answer, which the 15-minute lag margin covers; as the start of the next window it is never earlier than the answer, so a game that ended before the counter was read is never taken for a new one. A stored game that ended less than 15 minutes before the snapshot, or after it, does not count: it may not be in the counter, and must not stand for a missing game. A real listing queues its new ids in the outside-Master band (`fetch_rank` 100,000); a failed one waits 1 h. With `LISTING_SKIP=off` every moved counter is a listing. `outsideMasterChecks`, `extraPlayersPolled` (their listings) and `outsideMasters` (`followed`, `checkedLastHour`, `neverChecked`, `oldestCheckMinutes`, `toList`, `matchesWaiting`) in the minute `progress` log.

Also, at least hourly: Data Dragon check → new patch row + static data ingest (champions, spells, items, runes, summoner spells, per patch); keep only the 2 latest patches. A new patch is collected as soon as its static data is in. Whether it is live on a platform (at least one of its matches stored there) is derived from `matches`, read at startup and at each patch change, then set by the platform's first stored match of the patch (`latest patch is live` log line; `latestPatchLive` in the minute `progress` log); until then the previous patch is still collected there. Then older patch rows are deleted (→ cascades) and orphan non-tracked players are purged in small lock-safe batches (only after a deletion, and at startup); a cleanup failure is logged and retried 5 min later. Every cycle writes a `worker_runs` row; each platform loop upserts `worker_status` (heartbeat every 30 s, `auth_rejected_since` while Riot rejects the key, last error). Structured logs to stdout. **Puuids are never logged**: Riot request paths carry them, so the Riot client (`riot/client.ts`) redacts the request's puuid (raw and URL-encoded) from every error it throws (message and `path`) and every log line it writes; whatever logs or stores a Riot error downstream (`worker_status`, enrichment/daily failures…) never sees one. Graceful shutdown on SIGTERM. Config via env: `RIOT_API_KEY`, `DATABASE_URL`, `PLATFORMS` (default `KR,EUW1,NA1,VN2`), `LOG_LEVEL`, `COLLECT_PREVIOUS_PATCH` (`true` keeps collecting the previous patch after the latest is live, for a backfill by hand; default off), `LISTING_SKIP` (`off` | `shadow` | `on`, default `off`: level 2), `DIAMOND_MAX_TRACKED` (ceiling of the Diamond target per platform, default 0: level 1), `OUTSIDE_MASTER_CHECKS_PER_HOUR` (ceiling of the checks of level 6 per platform, default 1500; 0: the outside Masters are not followed) and `MASTERY_REFRESH_DAYS` (level 4, default 3).

## API

Bun + Hono, port `3000`. Read-only on match data. Owns the stats layer (added as migrations in `packages/db`), refreshed by the API on a timer (`STATS_REFRESH_MINUTES`, hourly) when new matches arrived; an advisory lock keeps instances from overlapping. A refresh has two parts (`docs/database-schema.md`, Stats layer). **Incremental tables** (`0030_incremental_stats.sql`) hold what is derived from one match alone: each participant's build, computed from that participant's own `participant_events` row (`stats_participants`), its support quest upgrade, the lanes of the match and its late-game swaps. A stored match never changes, so a refresh only computes the rows of the matches stored since the last one (`pl_stats_fill`; `stats_matches` records which are done), and deleting a match deletes its rows: this part no longer grows with the database. **Materialized views** aggregate those tables into what the API serves (`REFRESH MATERIALIZED VIEW CONCURRENTLY`) and are recomputed by every refresh, like everything that depends on a whole patch or on the present: composition traits (a team against the percentiles of its patch, applied when the aggregates are computed) and the tier list rank filter (the players' current rank). The result is always what recomputing everything would give: the only input of a row that can change later, the item data of its patch, is watched (a patch whose items were imported again with other flags is computed again), and `refreshStats({ rebuild: true })` recomputes every match. The worker only stores matches. There is no on-demand refresh. In-memory response cache (TTL ≈ 10 min) and a per-IP token bucket. Contract types live in `@pick-league/shared` (`api-contract.ts`).

**Behind a gateway.** The API is only called by the web app's server (Next.js on Vercel, which also proxies the desktop app's calls), over HTTPS through Caddy. No browser calls it, so there is **no CORS**.
- `API_TOKEN` (optional env). When set, every route except `GET /health` requires `Authorization: Bearer <API_TOKEN>` (constant-time comparison); otherwise `401 UNAUTHORIZED` with the usual error body. Unset (local dev): no auth.
- Client IP for the per-IP rate limit (and the request log): with a valid token, the visitor's IP the gateway sends in `X-Client-IP` (the socket's when the header is absent); without a token, the socket's, or the first `X-Forwarded-For` address with `TRUST_PROXY`. `X-Client-IP` is ignored on requests without the valid token.

Endpoints (v1):

- `GET /health` → `{ ok, db, latestPatch, matchCount, patchMatchCount }`: `latestPatch` is the patch the stats are served from (the newest kept patch with matches in the refreshed stats, see `stats_patch_matches`; the newest kept patch while none has any), `patchMatchCount` the matches stored on it. If the stats view cannot be read it falls back to the newest kept patch rather than failing.
- `GET /stats/status` → stats freshness `{ refreshing, lastRefreshedAt, lastRefreshDurationMs, matchesIncluded, matchesStored, pendingMatches }` plus `collection: { state, platforms }` read from `worker_status` (one cheap query, the desktop polls every 60 s): per platform `{ platform, heartbeatAt, authRejectedSince, lastError, lastErrorAt, lastMatchStoredAt }` (`lastMatchStoredAt` = newest `matches.fetched_at` of the platform; `lastError` is the worker's text with anything shaped like a player id replaced by `<redacted>` and cut to 300 characters, since this endpoint is public through the gateway); `state` is `key_rejected` when any platform has `auth_rejected_since`, else `stalled` when no platform heartbeated in the last 3 minutes (worker down; database clock), `unknown` without rows (worker never ran or predates 0009), else `collecting`.
- `GET /patches` → kept patches with match counts per platform.
- `GET /static/:patch` → champions (id, slug, name, tags, spells), items, runes, summoner spells — what the desktop needs to render icons/names. Image URLs are Data Dragon CDN URLs. `latest` here is the newest ingested patch (a new champion's name and icon exist before its first match), while `patch=latest` for the stats (tier list, recommendations) is the patch the stats are served from, as in `/health`.
- `POST /recommendations/picks` — body: `{ role, allies: [{championId|null, role}], enemies: [championId|null], bans: number[], availableChampionIds?: number[], masteries?: [{ championId, points }] }` → ranked candidates `{ championId, score, confidence, patchesUsed, reasons: Reason[] }`. When an enemy is (guessed to be) the lane opponent, each candidate gets a `lane_phase` reason at 10 min right after that matchup reason (see Engine, lane phase). When `masteries` (the user's own mastery points, at most 400) is present, each candidate gets a `mastery` reason whose delta is added to its score (a champion not listed counts as 0 points); absent, nothing changes.
- `POST /recommendations/build` — body: `{ championId, role, allies: [{championId, role}], enemies: [{championId, role|null}] }` → `{ patchesUsed, items: { starting, early, core, situational, lateSwaps, questUpgrade? }, runes, summonerSpells, skillOrder }` (`questUpgrade`: supports only, the support quest upgrade to pick), every piece with `reasons: Reason[]`. `items.late`: `{ itemId, games, share, reasons }[]`, the late items: the non-boots items most often completed after the core (usual slot from `coreSize` + 0.5 on, i.e. fifth completed item or later), at most `maxLateItems` (3), each built by at least `lateItemMinShare` (10 %) of the players who get that far into their build (`share`, against `stageReference` at the item's usual slot), none of them in a core build or situational; `items.lateSwaps`: `{ sellItemId, buyItemId, games, minute }[]`, the champion + role's late-game swaps (see Engine, late-game swaps), at most 3, often empty, in reading order: a swap only sells an item of the core builds or late items shown, a pair of boots or the item bought by a swap listed before it, and among those the most frequent comes first; they have no reasons and no win rate, and depend on the allies and enemies only through the core builds. Optional `lanePhase: Reason[]`: `lane_phase` reasons at 10 then 15 min for the locked champion vs the primary lane opponent (the one the build adapts to), each only with enough matchups; absent without a lane opponent.
- `POST /recommendations/draft` — body: `{ allies: [{championId, role|null}], enemies: [{championId, role|null}], side: 'blue'|'red'|null, platform?: 'KR'|'EUW1'|'NA1'|'VN2'|null }` (a draft in any state, the probability is the allies'; `platform`, optional, is the server the match is played on: the side edge is then that platform's) → `{ patch, patchesUsed, winProbability, reasons: Reason[], damage: { allies, enemies }, gameLength: { allies, enemies } }`. See Engine, draft evaluation. `damage` per team: `{ physical, magic, true, champions: [{ championId, physical, magic, true }] }`, each champion's average damage to champions per minute (`stats_champion_traits`, all roles) split by type. `gameLength` per team: `{ early, late, champions }`, the sum of the early / late deltas of its champions in their given or guessed roles (see Engine, game length; `champions` = those with a profile); it never changes `winProbability`. Used by the draft planner and by champion select (in game too).
- `GET /tierlist?role=UTILITY&patch=latest` → `{ role, patch, filters, roleGames, entries }`: every champion of the role with ≥ `minCandidateGames`, scored by its win-rate delta vs the role average (shrunk like the picks engine), tiered S–D by score percentile (non-positive scores capped at B), with win/pick/ban rates (pick rate = share of matches where the champion is picked in the role: its games over half the role's games), confidence, `patchesUsed` (per champion: the previous patch listed while it still weighs ≥ 10 %, see Engine). Ban rates come from the `stats_champion_bans` / `stats_patch_matches` views. Kept light (~15 KB per role): relations come from the next endpoint.
  - **Filters** `platform=ALL|KR|EUW1|NA1|VN2` (default `ALL`) and `rank=DIAMOND|MASTER|GRANDMASTER|CHALLENGER` (default `DIAMOND` = "Diamond+", every stored game), echoed as `filters` in the response; the cache key includes them. Everything else (per-champion patch weighting, percentile tiers, pick rate, `roleGames`) is computed the same way on the filtered rows.
    - Server: only matches of that platform (`matches.platform`).
    - Rank: applied per counted participant, on the player's **current** solo tier (`players.solo_tier` when the stats are refreshed — from the ladders for tracked players, from enrichment for the others — not the tier at match time). `MASTER` keeps participants whose player is Master, Grandmaster or Challenger, `GRANDMASTER` Grandmaster or Challenger, `CHALLENGER` only Challenger ones (`rank_level` 1 / 2 / 3 since `0029_tierlist_master_filter.sql`). A matchup/duo row counts when the champion's own player qualifies (the opponent's/partner's rank is not looked at). `DIAMOND` (shown as "Diamond+", the default) counts every participant of the stored matches: the matches of Master+ lobbies and, since the worker tracks Diamond players (`DIAMOND_MAX_TRACKED`), the games of the tracked Diamond players. Before Diamond was tracked, when each match was listed from a tracked Master+ ladder player, about 1 counted participant in 6 was currently below Master (16.8 % on 16.22, Nov 2026: Diamond 14.9 %, Emerald 1.6 %, lower 0.3 %; unknown rank 0.03 %). They stay in the default view so it is the full sample; they are excluded by the two other rank filters. With `DIAMOND_MAX_TRACKED` the worker also stores the matches of tracked Diamond players, including lobbies without any Master+ player: they are in the default view (and in every unfiltered statistic) like the rest, so "Master+" then means "Master+ lobbies and the lobbies of the tracked Diamond players".
    - Ban rate under filters: `(counted participants whose match banned the champion) / (counted participants)` — the share of the counted players' matches where it was banned, a match weighing once per counted player in it. With every participant counted (server filter only) that is exactly banned matches / matches of that server.
    - Default filters read the unfiltered views (same response as without filters). Other filters read `stats_tierlist_*` views (`0006_tierlist_filters.sql`), kept per (patch, platform, rank level) and summed at request time; they only hold lane-opponent and duo-partner pairs, which keeps them about the size of `stats_champion_vs` (all ally pairs would be ~3.4× bigger).
- `GET /tierlist/champion?role=UTILITY&championId=111&patch=latest` (same query as `/tierlist`, filters included, plus the champion) → `{ role, patch, filters, championId, patchesUsed, games, winRate, matchups, duos, synergies, gameLength? }`: fetched when a champion is selected in the tier list. Every lane opponent (`matchups`), duo partner (`duos`) and ally in the other roles (`synergies`) with ≥ `tierList.minRelationGames` (5) effective games (each relation measured per patch, then blended like the champion's own record, see Engine), as `{ championId, role, delta, winRate, games, confidence }` (confidence = n / (n + k) with the picks engine's `confidenceK.matchup` / `duo` / `pair`), sorted by shrunk delta (best first, worst last). Matchups also carry `lane` (lane-phase difference at 10 min, see Engine) when the sample allows and no server/rank filter is active. Inline in `/tierlist` this would be ~1 MB per role. With server/rank filters, matchups and duos come from the filtered views and `synergies` is `null` (the filtered views have no other-ally pairs). `gameLength` (`{ early, late, earlyGames, lateGames }`, see Engine, game length) is omitted with server/rank filters or when neither delta has enough games.

Requests: POST bodies are capped at 64 KB (`413 PAYLOAD_TOO_LARGE`), `availableChampionIds` at 1000 ids, `masteries` at 400, the other lists at a team's size. A requested champion (`championId` of a build or of `/tierlist/champion`) that is unknown — including ids beyond the `smallint` id columns — gives `404`; ids inside lists that match no champion are ignored (the League client may send ids beyond that range). The response cache stores a computed response only if no stats refresh cleared the cache meanwhile, runs one computation per cache key at a time, and is cleared after every refresh, including one that failed after refreshing some views.

`Reason = { kind: 'matchup'|'duo'|'vs_comp'|'with_comp'|'base'|'item_swap'|'lane_phase'|'mastery'|..., label: string (human readable), delta: number (win-rate delta, e.g. +0.028), games: number, lane?: { minute: 10|15, gold, xp, cs, duo, games } }`.

### Engine (inside the API)

- **Picks** — for each candidate champion in the requested role, an estimate of its win-rate difference, summed from shrunk deltas (every weight 1, `engine/config.ts`):
  1. its own strength: win rate in the role vs the role average,
  2. lane matchup (vs. the enemy in the same role, or all known enemies weighted by role probability if roles unknown; bot lane: both enemy bot laners),
  3. duo synergy (UTILITY↔BOTTOM, MIDDLE↔JUNGLE, TOP↔JUNGLE) and the other allies and enemies pairwise,
  4. vs. enemy / with ally composition traits,
  5. the player's own mastery of the candidate, only when the request carries `masteries`: from `stats_champion_mastery` (`0035_mastery_pre_game.sql`), the win rate of players in the same mastery bucket (edges 5k / 20k / 50k / 100k / 200k / 500k points) compared with the champion's average, counted only on the masteries fetched **before the game** (`champion_masteries.last_played_at`, Riot's `lastPlayTime` = the end of the player's last game on the champion, earlier than the match's start). Until 0035 every participant with a mastery row counted, but the worker often fetches the row right after storing the match (a first game on a champion asks for it at once), so the points included the game and the later ones: a player who lost their first game on a champion stays under 1,000 points (those slots won 5.4 %, against 43.6 % for the same points fetched before the game), and the curve was ~2.8× too steep (−9.2 points under 5k … +1.3 from 500k on 16.22 + 16.23; the held-out weight of 1.04 could not see it, training and test sharing the snapshot). The pre-game rows are ~8.5 % of them (548k of 6.5M participants on 16.22 + 16.23; more of the recent matches). The delta is the curve of all champions (each champion's wins above its own average in the same pre-game rows, per game of the bucket): −2.8 points under 5k, −2.2 for 5k–20k, −1.0 for 20k–50k, −0.6 for 50k–100k, +0.2 for 100k–200k, +0.6 for 200k–500k, +0.9 from 500k. A champion's own deviation from the curve is no longer used (`shrinkK` = Infinity, was 1,000): on held-out matches it predicted nothing (weight −0.05 ± 0.17 next to the curve). Added as is (weight 1, `ENGINE_CONFIG.mastery`): scored on the pre-game participants of the latest 20 % of 16.23 by start time with statistics from the earlier matches (`apps/api/scripts/calibrate-mastery.ts`), its weight is 1.17 ± 0.11 (1.08 ± 0.13 with the latest 10 % held out, 1.31 ± 0.12 with 40 %), where the old curve weighed 0.53–0.57. It takes no part in the confidence.
  A pair delta is the candidate's win rate vs/with that champion minus its own baseline, **minus what the role usually gets vs/with that champion** (games-weighted over every candidate): an enemy's own strength is the same for every candidate and must not favour the ones with small samples. Each delta is shrunk toward 0 (`delta * n / (n + k)`) with a `k` measured on the data: base 250, lane 900, other bot laner 2,400, duo 3,000, other allies 7,500, other enemies 3,500, composition traits 3,000. On 16.22 (~300k matches) the champion's own strength is the largest real effect (±3.3 points), lane matchups ±1.4, duos ±1.1; enemy composition traits had no measurable effect. The `k` of each pair kind is the one at which its held-out weight is 1. They were first measured with statistics from a random 80 % of the 16.22 matches, scored on the other 20 % (lane 600, other bot laner 1,600, duo 4,000, other allies 10,000; summed score slope 0.98 ± 0.04), but a random split leaks same-day and same-player information. Replaying production over the 8 days of 16.23 (each day predicted from all of 16.22 + the earlier days of 16.23, 346k matches) gave held-out weights of base 0.93–0.98, lane 0.85, other bot laner 0.6–0.76, other enemies 1.2, duo 1.4–1.5, other allies 1.1–1.3 and a summed slope of 0.92 (log-loss 6878.0e-4, coin flip 6931.5e-4); the current `k` are a log-loss refit on days 1–4 checked on days 5–8 (base and other enemies unchanged), with a slope of ~0.96 on the later days. `apps/api/scripts/calibrate.ts` re-measures them, by default with statistics from the earlier matches of a patch and the latest 20 % by start time scored (`--split hash` for the random split). Reasons are listed lane > duo > mastery > comp > base. Exclude banned and already-picked champions; if `availableChampionIds` is given, restrict to them. Confidence derives from sample sizes.
- **Composition traits** come from the data, not hand-written lists: per champion, average physical/magic/true damage share, damage taken + mitigated (tankiness), CC time, healing, plus Data Dragon tags and attack range. Team traits = aggregates of its 5 (or known) champions bucketed (e.g. "AD-heavy", "high CC", "high healing", "tanky", "poke/ranged").
- **Builds** — layered: (1) base = most successful choice for champion+role, scored by shrunk win-rate delta + a popularity bonus, **compared with the other choices of its kind** (the games where it exists: a 3-item path only among games with 3 completed items) with a `k` per kind measured on the data (keystone 700, spells 800, starter 1,200, boots 300, skills 300–450, items 200; quest upgrades and primary minor runes show no measurable difference, so popularity decides). Rune pages are built step by step among the pages of the chosen keystone (secondary tree + its runes, each minor rune, each shard), and the first three items one at a time (first, then second after it, then third): whole pages and paths are too fragmented (the most successful whole page used to be one seen in a few dozen games). Starter, boots, core completed with the most built items (from the participant's item events in `participant_events`, replayed with undo handling, ignoring consumables/trinkets/components); (2) adjusted for the lane opponent, (3) item swaps driven by enemy traits with data-backed deltas where samples allow, else Data Dragon item tags (anti-heal vs healing, armor vs AD-heavy, MR vs AP-heavy, tenacity/QSS vs CC, armor pen vs tanky), (4) situational items also answer the own team: the duo partner(s) (`stats_choice_duos`, reason `duo` with the partner in `championIds`) and active ally composition traits (`stats_choice_ally_traits`, reason `with_comp`), data-backed only (no tag rules); every context (lane opponent, enemy traits, duo partners, ally traits) is ranked by its best swap's delta before the situational cap, so an item answering several goes to the one it helps most, and a core item doing notably better with the duo partner or an ally trait gets that reason too. **An item's delta compares its builders with the players who got as far into their build** (kind `items_done`, `0015_items_done.sql`: players with at least its usual slot of completed items, interpolated), in the context and overall: compared with every game, late items looked several points better just because games where players complete more items are won more. Same layering for runes (keystone), summoner spells, skill order (first 3 levels + max order). Each choice carries reasons.
- **Late-game swaps** — `stats_item_swaps` (`0022_item_swaps.sql`): per (patch, role, champion), which completed item players sell once their build is full and which completed item they buy in its place (Guardian Angel → Bloodthirster, Mejai's Soulstealer → Rabadon's Deathcap, one pair of boots → another). A swap is the sale of a completed item whose next item event of that player is the purchase of another completed item at most 60 s later (a sale followed by its undo is a sale taken back), that purchase not being undone right after, by a player who had already bought at least 6 distinct completed items (boots included; without that rule the pairs are mostly early boots changes and Mejai's sales); a pair counts once per player and match. The build response lists pairs seen in at least `lateSwaps.minGames` (10) games, at most `lateSwaps.maxShown` (3), each with its games and the average game minute of the sale, **in reading order**: a pair is only listed when its sold item is an item of the core builds or late items shown, a pair of boots (whichever the build shows) or the item bought by a pair listed before it, and among those the most frequent is taken first (a champion's most frequent swaps can all sell an item its builds never mention — Xayah's sold Guardian Angel, which she builds as a fifth or sixth item: it is one of her late items; an item that only comes through a swap is listed after the swap that buys it). The current and previous patches are summed, unweighted (the samples are thin: about 1.5 % of the players of a match make one), independently of the build's own patch weighting; a pair with an item the current patch no longer has is left out. It **explains and never scores**: no win rate and no delta (players who can afford a swap are in long games they are winning), and it changes nothing in the recommended items. Unfiltered data only.
- **Lane phase** — `stats_champion_lane_phase` (`0010_lane_phase.sql`) reads the per-minute frames of `participants`: per (patch, role, champion, lane opponent) the average total gold / XP / CS difference at 10 and 15 min (each with its own matchup count: shorter matches have no 15-minute frame). Top, jungle and mid compare the two players (1v1); the bot lane compares the 2v2 (own + duo partner vs both enemy bot laners), since support gold alone says little. It produces `lane_phase` reasons that **explain and never score**: `delta` 0, `games` = matchups, numbers in `lane`. Patches are combined like the rest (the previous patch's matchups count for at most `previousPatchPrior.pair`, sums weighted by matchups), each average is shrunk toward 0 with `x * n / (n + k)` (`lanePhase.shrinkK` = 20 in `config.ts`: the per-match spread of a 10-minute gold difference is much smaller relative to matchup effects than a win/loss) and it is only shown from `lanePhase.minGames` (20) matchups. Unfiltered data only.
- **Game length** — `stats_champion_game_length` (`0019_game_length.sql`): games and wins per (patch, role, champion) in three buckets of `matches.duration_s`: under 25 min, 25 to under 32 min, 32 min or more. A champion's `early` (resp. `late`) delta is its win rate in games under 25 min (resp. of 32 min or more) minus its overall win rate, minus the same difference for the whole role, shrunk toward 0 with `x * n / (n + k)` on the effective sample of "the bucket vs the champion's other games", n = 1 / (1 / n_bucket + 1 / n_other) (`gameLength.shrinkK` = 300); null under `gameLength.minGames` (100) games in the bucket. The current and previous patches are summed (independent of the per-champion patch weighting). A team's profile is the sum of its champions' deltas. It **explains and never scores**: tier list champion details and the draft evaluation only. Unfiltered data only.
- **Draft evaluation** (`engine/draft.ts`) — the picks engine's deltas summed per team: P(allies win) = 0.5 + side edge + (Σ allies' strength − Σ enemies' strength) + (Σ ally–enemy pairs + Σ ally pairs − Σ enemy pairs), clamped to 5–95 %. A champion's strength is its shrunk win rate in its role vs the role average; each pair counts once, averaged over both points of view (ally–enemy: (a vs e − e vs a) / 2; teammates: (a with b + b with a) / 2), each delta centered and shrunk as in the picks engine. Unknown roles are guessed (`assignRoles`) and weighted by their probability; champions not picked yet count as average. The side edge comes from `stats_side_wins` (per patch and platform, `0034_side_wins_per_platform.sql`): the side's win rate on the current patch, with the previous patch as a prior worth at most `previousPatchPrior.side` = 20,000 games, on the request's `platform` when it has results there (prior capped at `sidePlatform` = 5,000 games), else on every platform. It moves between patches and differs between platforms: blue won 48.64 % of the 16.22 matches and 49.48 % (±0.17) of the 16.23 ones (16.22 / 16.23: EUW1 46.9 / 48.3, KR 49.0 / 49.8, NA1 48.8 / 49.2, VN2 50.1 / 50.8); both patches summed unweighted, as before, left every blue probability of 16.23 ~0.85 points too low (no side edge at all did better), and the per-platform edge gains ~1.5e-4 of log-loss over the all-platform one (VN2 −8.7e-4). The weights (`ENGINE_CONFIG.draft`, `baseWeight` / `pairWeight`) are 1: with the picks engine's `k` the summed score is close to calibrated on held-out matches (slope 0.98 ± 0.04 measured with a random split of 16.22; the temporal replay of 16.23 gives 0.92 with the earlier `k`, ~0.96 on its later days with the current ones, see Picks). Reasons (`base`, `matchup`, `duo` / `with_comp`, `side`) are sorted by |delta|, from the allies' point of view.
- **Previous patch as a prior** — every statistic is computed per patch against that patch's own baselines (the champion's win rate, the role average, the usual term), then the two patches are averaged with weights current games and `min(1, cap / previous games) × previous games`: the previous patch counts for at most 5,000 games per champion+role and per pair statistic (`ENGINE_CONFIG.previousPatchPrior`, `strength` / `pair`), so it fades as the new patch is played, with no threshold. Builds weight a champion+role's previous-patch rows by one factor (cap 20,000: a build splits the games between many choices and contexts, so it needs far more of them), which keeps its choices comparable. Effective games are what shrinkage and confidence use; a champion+role's own `games` (tier list entry and detail, pick candidates, `base` / `patch_fallback` reasons) shows its real games on the patches listed (both patches' full counts while the previous one is listed, else the current patch's), while pair statistics (matchups, duos, synergies, traits, lane phase, builds) show the weighted sample (rounded); `patchesUsed` (newest first) lists the previous patch while it weighs ≥ 10 %; a `patch_fallback` reason says "Mostly … data" while it weighs ≥ 50 % (not when the whole role has no game on the current patch yet). Why: simulated inside 16.22, dropping the previous patch at 150 current games left the strength estimate off by 1.06–1.50 points, against 0.65–0.80 with this prior (summing both patches forever was 0.43–0.73 inside one patch, but a real new patch changes champions). That cap was 1,200 games; replaying the 8 days of 16.23 (each day predicted from all of 16.22 + the earlier days of 16.23), 5,000 did better from the second day on (slightly worse on the patch day itself): with the refit pair `k`, days 5–8 log-loss 6869.6e-4 → 6866.1e-4.

## Desktop helper

Electron (via electron-vite) + React + TypeScript. UI with shadcn/ui on Base UI, initialised **exactly** with `bunx --bun shadcn@latest init --preset b5Ku0GIBG --pointer`; components are added only through the shadcn CLI.

- **Shared UI** (`packages/ui`, `@pick-league/ui`, shadcn monorepo layout): the shadcn components (`components/ui/*`), the views a web app shows too (tier list, draft planner, build view, stats freshness / collection banner, reasons…), their hooks, the pure logic (`lib/draft.ts`, formatting, confidence…) and the theme (`styles/globals.css`: Tailwind, tokens, fonts, base styles, `@source` of the package). Imports are `@pick-league/ui/components/*`, `/lib/*`, `/hooks/*`, `/styles/*` (also inside the package); components with hooks or events start with `'use client'`. The views never touch `window.pickleague` nor the desktop's `AppState`: their API calls come from a `PickLeagueDataProvider` (`PickLeagueData`: tier list, tier list champion, generic build, draft picks / build / evaluation; plain serializable arguments and `ApiResult` answers — the desktop passes its IPC bridge, a web app its Server Actions) and the rest from props (static lookup, data key, and the League-client-only mastery / owned champions, hidden when absent). Viewer choices (tier list filters, minimum confidence, competitive draft) live in the browser's local storage. `shadcn add` from `apps/desktop` puts new components in the package (`components.json` aliases); champion select, settings, header and window chrome stay in the desktop.

- **LCU connection** (main process): find the running `LeagueClientUx` process and read `--app-port` / `--remoting-auth-token` from its command line (Windows: PowerShell `Get-CimInstance Win32_Process`; macOS/Linux: `ps`), falling back to the `lockfile` in the install dir. HTTPS with Riot's self-signed cert (trust it for `127.0.0.1` only), basic auth `riot:<token>`. Subscribe over WebSocket (WAMP, `OnJsonApiEvent_lol-champ-select_v1_session` and `OnJsonApiEvent_lol-gameflow_v1_gameflow-phase`). Reconnect when the client restarts (a WebSocket upgrade left unanswered gives up after 10 s and is retried).
- **Reads**: `/lol-champ-select/v1/session` (picks, bans, assigned positions, actions), `/lol-champions/v1/owned-champions-minimal`, `/lol-champion-mastery/v1/local-player/champion-mastery`, `/lol-summoner/v1/current-summoner`, `/lol-chat/v1/me` (only its `platformId`; the login packet's `platformId` as a fallback), `/lol-gameflow/v1/gameflow-phase` (a champion select that ends into a game stays shown, with its build, until the game ends — also while the client is closed during the game, until a reconnected client reports a phase outside the game or a new champion select), `/lol-gameflow/v1/session` (teams of a game already in progress when the app starts; player ids matched against the user's own to find their team, never sent anywhere).

Rune page: create/replace one page named `PickLeague` via `/lol-perks/v1/pages`; if no slot is free and no `PickLeague` page exists, warn instead of deleting a user page. Spells: `PATCH /lol-champ-select/v1/session/my-selection` putting Flash on the key chosen in settings (D or F, F by default); a pair without Flash keeps the user's keys. **Never** pick, ban, lock in, accept, or reveal hidden player identities.
- **UI**: champion select view (allies/enemies/bans, my role), recommended picks with mastery badge on each champion icon and expandable reasons, ranked for the user's mastery: the picks request carries the user's mastery points per champion (points only: no Riot ID, no puuid; setting "Rank picks for my mastery", on by default; the draft planner and the web app do not send them); build view (lane phase vs the lane opponent, items in buy order, situational items, runes, spells, skill order) with reasons on every element, and under the item columns, when the champion has some, one "Late game" strip: its late items ("Then, most often": icon, name, "built by 65%", reasons on hover) followed by its late-game swaps ("Swapped at full build": sold item → bought item, "42 games · ~38 min", names in the tooltip; no win rate); lane-phase reasons shown as figures ("−420 gold · −8 CS · −310 XP at 10 min", "2v2" for the bot lane) and tier list matchups with their lane gold at 10 min ("+250g @10", CS / XP / sample on hover); tier list champion details show its early / late game deltas ("Early game +2.4%", "Late game −1.8%", games under 25 min / of 32 min or more); patch used + sample size; draft planner (works without the League client): a draft played by hand, ranked solo/duo by default — 10 bans alternating Blue/Red (skippable), then picks B1 R1 R2 B2 B3 R3 R4 B4 B5 R5 — or competitive ("Competitive" switch, remembered; changing it starts a new draft): 3 bans each (B R B R B R), picks B1 R1 R2 B2 B3 R3, 2 bans each (R B R B), picks R4 B4 B5 R5; each pick for a role the user chooses (the team's first open role by default). Dark mode friendly. Icons from Data Dragon CDN.

## Web app

Next.js (App Router) in `apps/web`, deployed on Vercel (root directory `apps/web`). Same shared views and theme as the desktop (`@pick-league/ui`, shadcn components added only through the CLI, `components.json` aliases into the package), minus what needs the League client (champion select, auto-apply, mastery / owned champions, settings, window controls). Routes: `/` tier list, `/draft` draft planner; the root layout renders the header (API patch + matches, stats freshness, collection banner), the navigation (left rail, bottom bar on phones) and both views, kept mounted across routes like the desktop. The views render in the browser only (they read local storage and the platform on their first render).

- **Data**: `lib/api.ts` (`server-only`) calls `API_URL` with `Authorization: Bearer <API_TOKEN>` and the visitor's IP in `X-Client-IP` (first `X-Forwarded-For` address, else `X-Real-IP`; Vercel sets them). GETs use the data cache (`next.revalidate`, `lib/cache.ts`: static data 6 h, patches 1 h, tier list / champion 10 min, health and stats status 60 s; the cache key includes the headers, so answers are reused per visitor IP); POSTs are never cached. The root layout (Server Component) fetches static data, the header status and the first tier list; the views' `PickLeagueData` comes from Server Actions (`app/actions.ts`, arguments validated with the contract's zod schemas, answers are plain `ApiResult`s); the header status is polled every 60 s through a Server Action.
- **Gateway** (`app/api/v1/[...path]/route.ts`, `lib/gateway.ts`): forwards only the contract routes (`GET` health, patches, static/:patch, tierlist, tierlist/champion, stats/status; `POST` recommendations/picks|build|draft) with the token and the caller's IP, passing through status, `Retry-After` and the JSON body; other paths are `404 NOT_FOUND`, POST bodies over `MAX_REQUEST_BODY_BYTES` are `413`. Successful GETs carry `Cache-Control: s-maxage` (same lifetimes) for the CDN; POSTs and errors are `no-store`.
- **Env** (server-only): `API_URL`, `API_TOKEN` (`apps/web/.env.example`).

## Docker

- `docker-compose.yml` at the root: `postgres` (postgres:17, named volume, healthcheck, tuned for 12 GB: `shared_buffers` 3 GB, 1 GB `/dev/shm` for parallel queries), `worker`, `api` (published on `127.0.0.1:3000` only), `caddy` (ports 80/443, TLS for `PUBLIC_HOST`: a Let's Encrypt IP certificate on the short-lived profile when it is a bare IP, `deploy/Caddyfile`). Each service has a memory/CPU limit (Postgres 7 GB, API 1 GB, worker 512 MB, Caddy 256 MB). Images built from a single multi-stage `Dockerfile` using `oven/bun`. `restart: unless-stopped`, logs rotated (3 × 10 MB per container), `api` healthcheck on `/health`. `.env` provides `RIOT_API_KEY` (+ `POSTGRES_PASSWORD`, `PUBLIC_HOST`, `API_TOKEN`, `TRUST_PROXY`, optional `PLATFORMS` and API settings): only the worker receives the whole file, the API gets its own settings listed in the compose file, never the Riot key.
- `deploy/`: Caddyfile, and systemd timers installed by `deploy/install.sh`: a watchdog every 2 min (restarts a stopped/unhealthy service, or the worker when its `worker_status` heartbeat is over 5 min old), and a 5-minute sample of the worker's open HTTPS sockets.
- `docker-compose.override.example.yml` (publishes Postgres on 127.0.0.1:5432) and the `bun run dev:*` scripts let each app run outside Docker against the dockerised Postgres.
- `.github/workflows/desktop-release.yml`: a `desktop-v*` tag builds the Windows installer and attaches it to a GitHub release.
